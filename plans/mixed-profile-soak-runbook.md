# Mixed capacity/latency profile soak

This is the repeatable correctness and operational gate for `profile = latency`.
The gate is one uninterrupted 24-hour hardware run. A bounded local or mock run
validates the harness only and must say **NOT 24h / NOT hardware**. Keep commands,
source and binary hashes, all configs, startup logs, metrics, process status,
restart output, reference state, and the final verdict in a dated `bench/`
directory.

## Safety and compatibility boundary

- This procedure is **protocol v2 only**. Every PD, node, admin tool, and client
  must come from the same v2-compatible source. Never start a v1 binary on a
  corpus written by v2 and never use an old binary as the profile rollback.
- `format=true` is obsolete and rejected. An existing SPDK layout is reopened
  without provisioning. A fresh layout requires all daemons stopped and the
  destructive command `valsd provision -c NODE.conf --device PCI=SERIAL
  --confirm-destroy NODE_ID`. The owner has now authorized a fresh SPDK soak
  corpus and replacement PD test state, while retaining useful unresolved heap
  cores with matching binaries, the sealed cache, and compact provenance. That
  authorization permits later preparation after identity/exclusivity checks;
  no provisioning, binding, wipe, daemon start, or 24-hour run occurred in this
  harness-repair pass.
- Confirm PCI **and serial**, not historical `/dev/nvmeN` numbering. Preserve
  retained corpus, sealed cache, cores, and matching binaries unless the owner
  explicitly selects a disposable soak corpus.
- The hardware gate uses an RF=3 sorted test zone on three nodes. Every node
  config must contain `rf=3`, both peers, and normal nonzero `gc_grace` (use the
  production value, not zero). A single PD is acceptable only for the clearly
  labelled local developer preflight; use the deployed redundant PD topology for
  the hardware gate: three voting PDs, one per host, generated by
  `scripts/pd_topology.py` (as `bench/0471-queue-hw/hw.py provision --pd-mode three`
  does) and checked with `hw.py check-configs`
  ([Three-PD reference deployment](../docs/deploy.md#three-pd-reference-deployment)).
  `PD_HOST`/`PD_ADMIN_SOCKET` below may name any replica, because the zone-status
  hook only reads `zones` (a follower answers non-authoritatively); send mutations
  to the replica whose `status` shows `role=leader`.
- All three hosts must be NTP-disciplined. `profile-soak-remote-status.sh`
  measures each node's clock against the driver host on every scrape and fails
  the run above `MAX_CLOCK_SKEW_MS` (default 500 ms). The correctness model
  compares tombstone ages against `gc_grace` using wall-clock HLC high bits, so
  a skewed fleet clock is a correctness hazard, not just an annoyance.

## Bounded client, readiness probes, and half-open peers

The driver builds its transports with a **validated finite client config**
(`ClientConfig::default()` plus explicit overrides): a connect deadline
(`VALS_PROFILECHECK_CONNECT_DEADLINE_SECS`, default 5 s), an RPC deadline
(`VALS_PROFILECHECK_RPC_DEADLINE_SECS`, default 15 s) and the normal client
credit pool. Nothing in the harness uses the unbounded benchmark pool any more,
so a half-open TCP peer cannot park an await forever and defeat the retry,
outage and hook bounds above it.

`plans/profile-soak-probe-test.sh` proves that with real binaries: it points the
driver at a listener that accepts and never answers, at an unroutable address,
and at a refused port, and fails the test if any probe survives to the external
`timeout` kill instead of failing inside the driver's own deadline.

The same code path is the readiness check the wrapper uses. After every restart
hook (and before the workload, and after the final rolling restart) the wrapper
runs `vals-bench x profilecheck` in probe mode
(`VALS_PROFILECHECK_PROBE_NODE=N`, bounded by `PROBE_SECS`) against **each**
node: a real data RPC (point read plus a one-entry scan) to the configured test
zone. A listening TCP port or a live metrics endpoint is not accepted as
readiness evidence.

## Quorums actually exercised

The zone-status hook prints `declared_w`/`declared_r`. Those are **operator
intent recorded from `WRITE_QUORUM`/`READ_QUORUM`, not proof**. The quorums that
the run actually executes come from the driver:

- `vals-bench profilecheck` builds `Coordinator::new(.., quorum, ..)` with
  `quorum = nodes/2 + 1`, so a three-node run uses W=majority=2 and R=2.
- Coordinator writes use `WriteConcern::Majority`; coordinator reads use
  `read_in`, i.e. `r = quorum`.
- Direct `Apply`/`BatchApply` candidates are sent to every replica and the run
  fails unless at least `quorum` replicas acknowledged.

The executed value is printed as `quorum=N` in the `PROFILECHECK PASS` line and
the wrapper fails the long gate unless it is 2.

## Profiles, keyspace, and workload semantics

Start node 1 as capacity, node 2 as latency, and node 3 as capacity. Do not set
`VALS_BLIND_APPEND_LWW` or `VALS_WINNER_DIRECTORY`; daemon profiles are startup
authority. Node 3 must transition capacity -> latency -> capacity with the
current binary, and all nodes must be restarted while writes continue.

The wrapper validates the binding rather than assuming it: each entry of
`CONFIG_FILES` must declare `node_id` 1, 2, 3 in that order with profiles
capacity, latency, capacity; each config's `listen` port must match the same
node's `PEERS` address; each config's `metrics` port (when declared) must match
the same position in `METRICS`; every config must agree on one `gc_grace`; and
after the first scrape each metrics endpoint must report the bound startup
profile. `NODE_STATUS_CMD` must report exactly nodes 1, 2 and 3. Configs may use
either `key = value` or compact `key=value` syntax and may carry `#` comments.

`vals-bench profilecheck` uses seed identity `0x01945eeddeadbeef`. Its synthetic
versions take current wall-clock milliseconds in the HLC high bits and a
strictly monotonic low counter, so reusing a key inside one millisecond still
produces a strictly newer candidate, normal `gc_grace` does not reject them, and
no candidate is future-skewed.

The model keyspace is bounded, which is what makes 24 hours of driver RAM and
data pressure predictable:

- `SEED_KEYS` cold keys `seed-%08d` written once in bounded BatchApply chunks
  (the 24-hour mode requires at least 1,000,000).
- `WORKLOAD_KEYS` keys in each of five cyclic domains: `profile-`, `batch-`,
  `coordinator-`, `cas-`, `retired-`. Round *r* uses slot `r % WORKLOAD_KEYS`,
  so keys are rewritten cycle after cycle instead of growing without bound.
- The model maximum is `SEED_KEYS + 5 * WORKLOAD_KEYS`; the driver asserts the
  reference never exceeds it and refuses reference state that does.
- Each round also rewrites one cold seeded key, so overwrite pressure hits data
  that is already on disk rather than only fresh keys.

Every round sends out-of-order and exact-retry candidates for a reused key:
lowest version first as a put, a middle candidate of the opposite kind, and the
highest version applied twice. For roughly a quarter of the (cycle, slot)
combinations **the highest version is a tombstone**, so the winner is a delete;
the next cycle writes a strictly newer live value to the same key, which
exercises resurrection. The same pattern is used for repeated-key BatchApply.
`retired-` keys are written live and then deleted once during the first cycle
and never touched again, so their winning tombstones age past `gc_grace` in a
long run. `Won` and `Lost` are both successful unconditional acknowledgements;
neither response is used to infer the winner.

`gc_grace` must comfortably exceed the longest expected node outage plus the AE
repair delay. A replica rejects a *live* value whose version is older than
`now - gc_grace` (`live_admission_cutoff_ms`), so anti-entropy cannot repair a
write that became older than the grace window while a node was down. A
deliberate 2-second-grace local probe reproduced exactly that: three cold
overwrites stayed stale on the restarted node and the harness failed closed
(`bench/task-0194-harness-shortgrace-probe-20260909T0007Z`). Use the production
grace for the gate.

## Expected results, tombstones, and GC

Expectations are API-specific because the public surfaces differ:

- `Coordinator::read_in` filters tombstones, so a winning tombstone must read as
  absent. Any value, any older version, and any missing live winner fails
  immediately: quorum intersection makes those impossible, not merely slow.
- Per-replica `read` and `scan` expose tombstones as `(version, None)`. Inside
  `gc_grace` (minus a clock-skew margin, `VALS_PROFILECHECK_CLOCK_SKEW_MS`,
  default 1000 ms) the exact winning tombstone must be present. After the grace
  window an absent tombstone is accepted as collected. A resurrected value, a
  version above the winner, or a value mismatch at the winning version is never
  accepted at any age.
- A version *older* than the winner, or a missing live key on one replica, is
  treated as unconverged rather than fatal, and is retried on a bounded schedule
  (see below) before the run fails.

The grace used by the model is explicit: the wrapper extracts `gc_grace` from
the validated node configs, requires all three to agree, exports it to the
driver, and fails unless the `PROFILECHECK PASS` line reports the same
`gc_grace_ms`.

## Reference state, resume, and unknown winners

The reference file has a magic, format version, zone id, seed identity, seed-key
count, **workload-key cap, gc_grace, a clean-shutdown flag, the highest issued
HLC**, round, and exact `(Version, value-or-tombstone)` entries. It is
atomically synced **dirty before any workload mutation** (including before
initial seeding and every clean resume), after seeding, at bounded 15-minute
checkpoints, and clean at shutdown. Probe and verify-only invocations do not
change it. A wrong zone/seed count, different keyspace cap or grace, legacy
state, truncation, duplicate key, trailing data, a high-water below the state's
own highest version, or a reference larger than the bounded model is rejected,
so an incompatible old state can never be verified against a new run.

Resume is version-safe and fail-closed:

- A resumed process seeds its version source from `max(persisted high HLC,
  highest reference version)` and never reissues a version it may already have
  used, even if the wall clock stalls inside one millisecond or moves backwards.
  Server-stamped coordinator/CAS versions are folded into the same watermark.
- Only a state written by a **clean** shutdown is resumed by default. A state
  left by a killed or crashed driver is refused unless
  `VALS_PROFILECHECK_ALLOW_DIRTY_RESUME=1` explicitly authorises reconciliation,
  because rounds executed after the last checkpoint may have left winners the
  model does not know. Only the exact value `1` enables this; an absent variable,
  `0`, a clean loaded state, or a fresh run cannot reconcile. A persisted dirty
  state is dirty even when its round and reference are both still empty.
- When a replica answers a planned maximum candidate with `Lost(existing)` for
  an `existing` **above** the planned version, a normal/clean run fails before
  issuing any reconciling write. Only an explicitly authorised dirty resume may
  bump the version source past the observed version and re-apply its own known
  value with a strictly newer version; a second unknown winner in the same step
  fails the run. This policy covers initial seed batches, direct Apply,
  BatchApply, and cold-seed overwrites. Losing a deliberately lower candidate to
  the planned maximum, or an exact-retry loss to our own version, stays legal
  and silent.
- In an authorised dirty resume the same reconciliation is applied when a
  checkpoint read observes a version above the model
  (`PROFILECHECK RESUME_RECONCILE` lines, bounded by
  `VALS_PROFILECHECK_MAX_RECONCILES`). The unknown value is never adopted: a
  known value is written over it at a newer version. A quorum reconciliation
  only clears per-node divergence debt for destinations that acknowledged that
  exact replacement. Omitted destinations retain (or acquire) debt with their
  original first-seen timestamp and must prove the replacement by readback.
- A dirty resume must re-execute at least as many rounds as the crashed process
  attempted; anything it never revisits is caught by the strict final
  verification (higher version or unexpected extra key) and fails the run.

Runtime checkpoints do bounded rotating strong-read samples rather than serially
point reading a million keys, and additionally read the same rotating sample
from **every replica**. Divergence is tracked **per key**, not per node: a key
that fails on a replica is added to that replica's bounded pending set with its
first-seen timestamp and is re-read at every later checkpoint until it is
observed healed. A later clean sample of unrelated keys therefore cannot reset
the clock, and the run fails once any pending key stays unhealed longer than
`NODE_CONVERGE_SECS` (or once a replica accumulates more than
`VALS_PROFILECHECK_MAX_PENDING_KEYS` unhealed keys). Independently, a node that
accepts no direct write for longer than `MAX_NODE_OUTAGE_SECS` fails the run,
which bounds "one replica was down but quorum kept working".

Omitted writes are tracked as named debts, not as a counter. When a live
cold-seed overwrite is not acknowledged by a replica, the exact
`(node, key, version, value)` is recorded as a pending omission. The driver
refuses to reuse that seed key for a new client write until the debt clears
(`deferred_cold_overwrites`), re-reads it from the missing replica at every
checkpoint, and only clears it on an **exact** version+value readback from that
replica (`PROFILECHECK OMISSION_HEALED`). A resurrected or wrong value fails
immediately; exceeding the convergence window fails; and the run never repairs
a replica from the model. Before writing a clean final state, the driver drains
both named omissions and all per-node divergence debts with bounded read-only
readback. If any debt cannot be proved healed, the run fails while the last
persisted state remains dirty.

## Final verification

After the workload, the wrapper quiesces, waits for AE dirty gauges, performs
the final rolling restart with its own timeout, waits for AE again, re-checks
profile binding, and starts a fresh verify-only driver process. That process
reloads the persisted reference and **streams** paged scans from every replica,
merge-joining them against the sorted reference. It never buffers a second full
map, it fails on any unexpected extra key or out-of-order scan page, and it
never repairs the model from what it observes. Unconverged (stale/missing)
keys are retried on a bounded schedule (`VERIFY_CONVERGE_SECS`, polled every
`VERIFY_POLL_SECS`) so late AE healing is allowed, but the run only passes when
each replica finally matches exactly. Note that dirty-bucket gauges reaching
zero is *not* peer digest agreement; the streamed exact scans are the evidence.

The wrapper fails unless all three replicas emit a converged
`PROFILECHECK VERIFY NODE` line and the final `PROFILECHECK VERIFY PASS` marker
is present. The long-gate wrapper forces dirty recovery off and requires
`reconciled_winners=0`; reconciliation can validate a separate recovery drill,
but can never produce the clean 24-hour acceptance PASS.

final scan does not add a second copy. Throughput on real hardware will differ;
do not reuse the local ops/s figure.

## Deployed configuration and binary provenance

Live gauges cannot prove which config or binary a node actually runs. Both
status and restart hooks therefore report the **deployed** facts:

- `profile-soak-remote-status.sh` hashes the active node config, parses its
  `node_id`, `profile`, `rf` and `gc_grace`, hashes the **running** executable
  through `/proc/<MainPID>/exe`, and additionally hashes node 3's prevalidated
  capacity/latency alternates on the node itself.
- `profile-soak-remote-restart.sh` prints `CONFIG_BEFORE`/`CONFIG_AFTER` hashes
  around every restart and refuses to continue if the installed active config
  does not byte-match the intended alternate.
- The wrapper checks each reported deployed config hash against the validated
  local config set, requires the parsed `node_id` to equal the node position and
  the parsed profile to equal the expected matrix entry (tracking node 3's
  current expected profile across both flips), and requires the running daemon
  hash to equal `EXPECTED_VALSD_SHA256`. Before the workload or any restart it
  also requires the remote node-3 capacity and latency alternate hashes to match
  the retained local files exactly, and repeats that check after hooks. The
  24-hour mode refuses to start without the pinned binary hash. Results
  accumulate in `deployed-configs.log`.

Source provenance is equally explicit. The wrapper snapshots `git rev-parse
HEAD`, the full `git status --porcelain=v1`, and the source-only untracked list
before creating or writing OUT, so an OUT inside a clean checkout cannot dirty
its own provenance. If the captured tree is dirty it also archives
`source.patch` (tracked changes) plus `untracked-source.tar.gz`, verifies the
archive file list and every archived content hash against retained manifests,
and labels the run `source_state=dirty`. A required archive failure aborts the
run. The 24-hour gate **refuses a dirty tree** unless
`ALLOW_DIRTY_SOURCE=1` is set deliberately, in which case the archived
patch/untracked snapshot is the reproduction record. A clean committed source is
the expected way to run the gate; local harness tests may run dirty because they
carry the same archive.

   exact release `valsd`, `vals-bench`, and admin binary. Copy the three active
   node configs plus node 3's alternate latency config into the evidence
   directory. Confirm all binaries are current compatible protocol v2.
2. Read-only check all hosts: hostname/kernel, no unexpected `valsd`, unit
   state, retained cores/cache/corpus, PCI/serial binding, hugepages, AER, core

   its project core pattern restored, hugepages reserved, and its serving
   scratch PCI function moved from `nvme` to the approved SPDK driver before a
   later SPDK launch. Those are launch-time mutations and are not done by this
   preparation.
3. Use the owner's recorded authorization for a fresh v2 SPDK soak corpus and
   replacement PD test state. Stop everything, preserve the specified useful
   cores/binaries/cache/provenance, and complete PCI/serial plus exclusivity
   checks before offline provisioning. The authorization is recorded in
   `bench/review-preparation-20260908/README.md`; it is not evidence that the
   destructive step has already happened.
4. Prepare node 3 capacity and latency config files differing only in profile;
   both retain RF=3, both peers, the same nonzero GC grace as the other nodes,
   the same v2 data layout, and `format=false` if that inert legacy line is
   present. Configure the real sorted test zone and record its numeric id from
   `valsd admin ... zones`.
5. Install/copy the helper scripts with the source. Verify `timeout`, `curl`,
   `awk`, `sha256sum`, SSH BatchMode, passwordless narrowly scoped systemd
   operations, metrics access, admin socket access, and one of `nc`, `bash` or
   `ss` on each node for the data-port readiness probe. Remote hosts do not need
   `rg`.

The checked helpers are concrete:

- `profile-soak-remote-status.sh` SSHes to each host, resolves the remote
  systemd MainPID, emits remote RSS/VmSwap, and measures clock skew. It never
  reads local `/proc` for a remote PID.
- `profile-soak-remote-restart.sh` performs bounded health-checked restarts,
  transitions node 3 on restart 1 and 2 using prevalidated complete config
  files, rotates later node restarts, and performs the final rolling restart.
  Readiness is not "systemd says active plus the metrics port answers" — the
  metrics listener starts before the engine opens. Each restart waits for the
  unit to be active, the **data RPC port** to accept a connection, sampled
  engine gauges (`vals_free_segments > 0`) to prove the engine opened and swept,
  and profile-consistent blind-append/winner-directory state, including
  `vals_winner_directory_keys > 0` whenever the reported profile is latency.
- `profile-soak-zone-status.sh` asks the current matching admin binary for the
  catalog and proves the selected zone is sorted RF=3 while recording the
  operator-declared W/R (see "Quorums actually exercised").

Run each status hook manually with `SOAK_EVENT=status` or
`SOAK_EVENT=zone-status` before launch. Do not manually invoke the restart hook
as a preparation test because it changes daemon state.

## Timeouts

`HOOK_TIMEOUT` bounds one hourly hook (one node restart). `FINAL_HOOK_TIMEOUT`
bounds the final rolling hook, which restarts **three** nodes sequentially and
therefore cannot share the hourly bound. Both are validated against
`NODE_RESTART_TIMEOUT`, the per-node budget the wrapper exports to the hook:
`HOOK_TIMEOUT >= NODE_RESTART_TIMEOUT + 5` and
`FINAL_HOOK_TIMEOUT >= 3 * NODE_RESTART_TIMEOUT + 15`. The remote hook refuses
to run unless its own `HEALTH_TIMEOUT + SSH_TIMEOUT + 10` fits inside
`NODE_RESTART_TIMEOUT`, so the external bound genuinely covers every inner step.
Defaults: `NODE_RESTART_TIMEOUT=240`, `HOOK_TIMEOUT=300`,
`FINAL_HOOK_TIMEOUT=900`.

## 24-hour invocation

Export the helper environment once so the command strings are unambiguous:

```sh
export HOSTS='10.0.0.114,10.0.0.18,10.0.0.200' SSH_USER=why
export NODE_UNIT=vals-node METRICS_PORT=9464 DATA_PORT=7001
export NODE_CONFIG_PATH=/home/user/vals/run/node.conf
export EXPECTED_VALSD_SHA256=$(sha256sum target/release/valsd | awk '{print $1}')
export NODE3_ACTIVE_CONFIG=/home/user/vals/run/node.conf
export NODE3_CAPACITY_CONFIG=/home/user/vals/run/node3.capacity.conf
export NODE3_LATENCY_CONFIG=/home/user/vals/run/node3.latency.conf
export PD_HOST=10.0.0.114 PD_ADMIN_SOCKET=/home/user/vals/run/pd.sock
export REMOTE_VALSD=/home/user/vals/target/release/valsd
export ZONE=NUMERIC_SORTED_TEST_ZONE READ_QUORUM=2 WRITE_QUORUM=2

PEERS='1@10.0.0.114:7001;2@10.0.0.18:7001;3@10.0.0.200:7001' \
METRICS='http://10.0.0.114:9464/metrics,http://10.0.0.18:9464/metrics,http://10.0.0.200:9464/metrics' \
OUT=bench/task-0194-profile-soak-$(date -u +%Y%m%dT%H%M%SZ) \
BIN=target/release/vals-bench PROTOCOL_VERSION=2 MAX_AE_SYNC_ERRORS_DELTA=10000 \
CONFIG_FILES='evidence/node1.conf,evidence/node2.conf,evidence/node3.capacity.conf' \
EXTRA_CONFIG_FILES='evidence/node3.latency.conf' \
NODE_STATUS_CMD="$PWD/plans/profile-soak-remote-status.sh" \
ZONE_STATUS_CMD="$PWD/plans/profile-soak-zone-status.sh" \
RESTART_CMD="$PWD/plans/profile-soak-remote-restart.sh" \
plans/profile-soak.sh 24h
```

Do not wrap this in an unrecorded shell. Retain the expanded environment and
stdout/stderr. `24h` fixes the duration at 86,400 s. `gate` runs the same checks
at a configurable length: `DURATION` (default 7,200 s), `RESTART_INTERVAL`
(default 600 s; expected restarts = `DURATION / RESTART_INTERVAL - 1`, at least 2
for both node-3 flips), `MIN_SEED_KEYS` (default 1,000,000) and `TREND_SAMPLES`
(the final space/run trend window, default half the samples, capped at 120).
`DURATION` must exceed `gc_grace` plus one restart interval, so a short gate
needs a short `gc_grace` in the deployed configs. Its PASS line records the
duration, restart count, seed keys and grace. Commands and curl calls are bounded. Scheduling uses elapsed epoch
time rather than accumulated sleeps. A failed workload, status/scrape
supervisor, hook, coverage interval, restart count, transition, pressure check,
AE deadline, diagnostic verdict, or final verification propagates failure and
kills the remaining workload child.

The long modes check the run while it goes, so a failing gate stops within
minutes instead of at the end:

- After every minute sample: free segments stay positive, the restart-aware
  error counters (AE sync/rebuild errors and retries, region exhaustion, server
  errors, node-2 latency probes) stay within the same bounds as the final
  verdict, and in `gate`/`24h` the space/run trend check runs on the newest
  `TREND_SAMPLES` samples as soon as that many exist.
- The driver probes tombstone collection (`GC_PROBE_SECS`, default 300 s in
  `gate`/`24h`, off otherwise). Every probe reads up to 64 winning tombstones
  that are overdue (older than `gc_grace` + 1 s skew + `GC_OVERDUE_SECS`,
  default `2 × min(gc_grace, 1 h) + 300 s`) on each replica and prints a
  `PROFILECHECK GC_PROBE` line. The driver fails if a replica collected none of
  the overdue tombstones it could read, or still holds more than
  `GC_MAX_HELD_PCT` of them (default 10% in `gate`/`24h`). A replica still
  holding an older live value is tracked as a divergence under the usual
  convergence bound. `gate` and `24h` need at least one probe that read an
  overdue tombstone and some collected ones (`gc_probes`, `gc_collected` in the
  PASS line).
- `DIAG_CMD` (optional; `plans/profile-soak-remote-diag.sh`, needs `NODE_LOG`)
  runs every `DIAG_INTERVAL` (default 1,800 s in `gate`/`24h`): a `PERF_SECS`
  (15 s) perf profile of each node daemon and its WARN/ERROR/panic lines since
  the start. At the end, and on any failure, it copies each node's whole log
  since the start (`OUT/diag/*.log.gz`). Diagnostics never decide the verdict.
- The counter log also records `vals_ae_entries_applied`,
  `vals_expired_tombstones_skipped` and the `lonegc` merge count and input bytes.

On the 0471 queue cluster (three PDs, three SPDK nodes × 8 shards, transient
`vals0471-node` units) the environment above is generated by
`bench/0194-profile-soak/prep.py env`, and `bench/0194-profile-soak/run.sh
rehearsal|gate|24h BIN ZONE` wraps the invocation (see that directory's FINDINGS.md).
Sharded nodes need two things the single-listen local runs never exercised: each
config's `listen` port set must equal its `PEERS` port set, and the driver's direct
per-replica calls route by the zone's range map (fetched from the replica on
`StaleEpoch`) and scan one range slice at a time. Run the driver on a host that is
not memory- or IO-starved: on 2026-10-21 devbox stalled `timeout 10 curl` for
77 s under another project's load, so the gate ran its driver on lab-3. The
lab boxes ship uutils `date`, where `%3N` prints nine digits; the status hook
divides `%s%N` instead.

## Required evidence and verdict

The wrapper scrapes every minute and around each restart, reruns remote status
for current PIDs and clock skew, and records recovered scrape retries. Any
unrecovered coverage gap fails. It requires at least `EXPECTED_RESTARTS` restart events (23 hourly
in `24h`, `DURATION / RESTART_INTERVAL - 1` in `gate`),
write progress across each event, ordered node 3 transition hook records, and
matching pre/post node 3 profile metrics. Selected latency requires effective
blind append and winner directory both enabled; selected capacity requires both
disabled.

The `gate` and `24h` modes additionally force the coverage that makes the AE and GC
claims real: `REQUIRE_OMITTED_WRITES`, `REQUIRE_HEALED_OMISSIONS` and
`REQUIRE_COLLECTED_TOMBSTONES` are all mandatory and cannot be disabled, so a
24-hour run cannot PASS without at least one omitted replica write, at least one
omitted live cold-seed winner identified and read back exactly on the replica
that missed it, and at least one winning tombstone actually collected after
grace. The driver must also finish with `pending_omissions=0`. Local runs have
never observed tombstone collection (no run merges happen in a 70-second
file-backed run), which is precisely why that requirement is a hardware-gate
guard rather than a local one.

Counter verdicts sum positive interval deltas and treat counter decreases as
process restarts, so a final reset cannot erase prior errors, probes, retries,
or merge evidence; a missing or non-numeric counter sample is a diagnostic
failure rather than a silent zero. AE sync errors must remain below the explicit
run bound — the local lifecycle run does produce a few hundred during deliberate
outages, so budget them from evidence rather than assuming zero — while rebuild
errors and region exhaustion remain zero, retries are bounded, free segments
remain positive, latency probe deltas remain within the declared allowance, and
merges must have advanced during the 24 hours. The driver's own coverage is also
required: `quorum=2`, matching `gc_grace_ms`, and nonzero `winner_tombstones`,
`resurrections` and `cold_overwrites`.

`MAX_SERVER_ERRORS_DELTA` stays strict (default 0). Restarting a node under
traffic can legitimately produce a small number of `vals_server_errors` as
in-flight requests are cut — the local lifecycle run measured 1 on node 1 and 1
on node 3 across two restarts. Do not pre-widen the bound to avoid a failure.
If the gate trips on a small restart-attributable count, classify every error
from the retained node logs in the artifacts and only then re-run with an
explicit, justified bound; never widen it silently and never widen it for
correctness or unexplained errors.

Inspect the retained full time series for stable used/free segments and
resident-run bands, continuing merges, bounded space errors, latency
write-probe deltas, directory coverage/RSS, startup rebuild cost, crashes,
cores, kernel/AER events, and the known 0248 corruption signal. Any unexplained
anomaly is fail-closed even if the script printed PASS.

Only `profile soak 24h PASS` from the real hardware mode plus this manual
artifact review can satisfy task 0194's owed soak. `preflight`,
`lifecycle-test`, and local-runner verdicts explicitly cannot.
